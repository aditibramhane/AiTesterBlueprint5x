1. Objective

The goal of this test plan is to verify that the VWO login dashboard provides secure, reliable, and usable access to the VWO platform. Testing will confirm that authentication and recovery flows behave as specified, invalid input and failures are handled clearly, and supported experience, security, accessibility, integration, and performance requirements are covered.

< 2 secondsLogin page load-time target on standard connections
95%+Login success-rate target
99.9%Availability objective stated in the PRD

Targets are PRD objectives, not assumed pass criteria for every individual test. Measurement definitions, environment, and observation windows must be agreed before formal performance or KPI reporting.

2. Scope

In scope

  • Email/password authentication; field validation; authentication feedback, loading, success, and failure states.
  • Remember Me behavior, session creation, configurable session timeout, and secure sign-out/session handling where available in the test build.
  • Password reset/recovery, password requirements, and secure reset-token behavior.
  • Optional multi-factor authentication, enterprise SSO (including SAML/OAuth as applicable), and social identity-provider options when implemented and enabled.
  • Registration/free-trial navigation, product announcement and theme links/options, and successful transition to the VWO platform.
  • Responsive behavior, keyboard and screen-reader access, clickable labels, contrast, and WCAG 2.1 AA checks.
  • Transport/session security, rate limiting, privacy/compliance handling, authentication event analytics, and support entry points.
  • Page performance, availability/load behavior, browser/device compatibility, regression, and end-to-end user journeys.

Out of scope

  • Functional testing of experimentation, personalization, analytics, and other post-login product features beyond verifying the login hand-off.
  • Implementation or code-level verification of infrastructure internals not exposed to the approved test team; these require appropriate technical evidence from the owning team.
  • Future enhancements listed in the PRD (biometric authentication, adaptive authentication, and progressive web app), unless separately approved and delivered for testing.

Test design techniques

Use equivalence partitioning and boundary-value analysis for field and password inputs; decision tables for credential/authentication combinations; state-transition testing for login, MFA, reset, and session states; use-case testing for new and returning user journeys; and error guessing/exploratory testing for usability and recovery issues.

5. Defect reporting procedure

  1. Log each reproducible deviation in the project defect-tracking tool. Include a concise title, environment/build, preconditions, sanitized test identity reference, steps, expected and actual results, severity/priority, and evidence.
  2. Do not attach passwords, reset tokens, session cookies, personal data, or other secrets. Redact network traces and screenshots before sharing.
  3. Triage with QA, product, engineering, and security owners as appropriate. Security/privacy issues should use the approved restricted reporting channel.
  4. After a fix is available, retest the failed scenario and run focused regression around the affected authentication/session path; update status with evidence.
  5. Share cycle-level defect status and unresolved release risks with stakeholders before exit/closure approval.
SeverityGuideline for this product
CriticalUnauthorized access, broad authentication outage, or exposure of credentials/session secrets; stop release assessment and escalate immediately.
HighCore login/recovery unavailable for a material user path, session security failure, or significant compliance/accessibility blocker without a safe workaround.
MediumLimited-scope functional or integration failure with a workaround, or significant usability issue not preventing all access.
LowMinor visual/content issue or low-impact inconsistency with no material security or access impact.

Final severity assignment and service-level targets follow the project’s defect-management policy; no response-time SLA is specified in the PRD.

6. Test strategy

  1. Requirement analysis and design: Review the PRD, clarify open policy/configuration items, create traceable scenarios and cases, and prioritize by user impact and security risk.
  2. Build smoke test: Confirm the login page renders, primary fields and controls work, and the critical authentication path can be attempted. Reject an unstable build for deeper testing and report blockers.
  3. Functional and integration testing: Execute positive/negative login, validation, recovery, session, MFA/SSO, navigation, analytics, and support scenarios enabled in the build.
  4. Quality attributes: Run responsive/compatibility, accessibility, authorized security checks, and performance/load tests using agreed environments, thresholds, and test data.
  5. Regression and retesting: Retest fixes and run the critical-flow regression set after changes. Repeat relevant cases for configured login methods and supported themes.
  6. Reporting: Maintain execution results, defects, requirement traceability, risks, and a cycle summary. Perform exploratory testing alongside planned cases.

Testing is risk-based and iterative. Testers should use only authorized test environments and accounts; security testing must remain within the approved assessment scope.

9. Entry and exit criteria

Requirement analysis

Entry: PRD and related product details are available to QA.

Exit: Requirements are reviewed; testable behavior and unresolved policy/configuration questions are recorded and assigned.

Test design

Entry: Scope and available requirements are understood.

Exit: Prioritized scenarios, test data needs, and expected results are documented and reviewed by the responsible stakeholders.

Test execution

Entry: Approved build and environment are available; critical test identities/configuration are ready; smoke test passes; test cases are reviewed.

Exit: Planned cases are executed or explicitly marked blocked/deferred; critical defects are triaged; fixes are retested; results and residual risks are reported. Any unexecuted scope has an owner and rationale.

Test closure

Entry: Execution and defect reports are available.

Exit: Test summary is delivered; remaining defects and accepted risks are documented; stakeholders provide the required release/test approval.

Release recommendation must account for unresolved critical/high defects and applicable security, privacy, accessibility, and performance risks. The PRD does not define defect-free numeric release thresholds; those require stakeholder agreement.

10. Test execution

Smoke-test checklist

  • Login page loads and displays the expected VWO branding and primary controls.
  • Email/password fields accept input; labels, password visibility behavior, and primary action are usable.
  • A valid authorized test identity can attempt authentication and receives the expected result.
  • An invalid attempt produces a clear, safe error; loading feedback resolves and does not leave the form stuck.
  • Recovery and registration links navigate to their expected destinations.

Representative end-to-end journeys

JourneyExpected outcome
Returning user logs in with valid credentialsAuthentication succeeds, any configured challenge is completed, and the user reaches the VWO dashboard.
User submits invalid or incomplete credentialsInline validation or authentication error is clear and actionable; access is not granted; sensitive details are not exposed.
User recovers a forgotten passwordRecovery instructions follow the configured policy; valid reset succeeds; invalid/expired/reused reset tokens do not change the account.
User chooses Remember MeSession persistence follows the configured behavior and timeout; disabling it does not retain the session beyond the expected policy.
Enterprise user signs in through configured SSO/MFAConfigured identity challenge completes and returns to the correct VWO destination; cancellation and errors are handled safely.
New user selects free trialRegistration path opens correctly without disrupting existing login flow.
User navigates the form without a pointerAll controls are reachable, visibly focused, operable, and announced with meaningful labels/status.

11. Test closure

At closure, QA will provide the final test summary, coverage and execution status, open/accepted defect list, environment/build details, measured performance observations, and known limitations. Test closure indicates completion of the planned assessment; it does not replace product, security, privacy, or release-owner approval.

13. Risks and mitigations

RiskMitigation
QA/pre-production environment or identity provider is unavailable or differs from production.Confirm access/configuration before execution; record differences; use alternate planned QA work while blocked; assess production-like coverage before sign-off.
Requirements for password policy, session timeout, MFA recovery, SSO, or rate limiting remain undefined.Raise clarification items early; do not assert undocumented behavior; obtain product/security decisions before final acceptance.
Limited time for cross-browser, accessibility, security, and load coverage.Prioritize critical login/recovery/session paths and security risks; record deferred coverage and residual risk; request resources based on scope.
Real user credentials or personal data are used in evidence or test telemetry.Use dedicated test accounts and synthetic data; redact evidence; restrict access and follow approved data-retention practices.
Load or security testing affects shared services or users.Run only with written authorization, agreed profile, isolated test identities, and a defined window/stop condition.
Third-party authentication or analytics service failures block end-to-end testing.Coordinate provider readiness; capture dependency/configuration failures; test product-side error handling and clearly mark provider-dependent cases.
